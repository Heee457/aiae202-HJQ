## 定义 AI 智能体及其类型

### 什么是 AI 智能体？

有一个简单的理解方式：

> **AI 智能体是让大语言模型（LLM）真正*做事*的系统——通过给它工具和知识，让它作用于外部世界，而不只是回复提示词。**

我们把这句话拆开来看：

- **系统** —— AI 智能体不是单一的一个东西，而是一组协同工作的部件。每个智能体的核心都有三部分：
  - **环境** —— 智能体工作的空间。对旅行预订智能体来说，这就是预订平台本身。
  - **传感器** —— 智能体如何读取环境的当前状态。我们的旅行智能体可能会查酒店空房或机票价格。
  - **执行器** —— 智能体如何采取行动。旅行智能体可能会订房、发确认信息，或取消预订。

![什么是 AI 智能体？](../../../01-intro-to-ai-agents/images/what-are-ai-agents.png)

- **大语言模型** —— 在 LLM 出现之前智能体就已存在，但正是 LLM 让今天的智能体如此强大。它们能理解自然语言、结合上下文推理，并把含糊的用户请求变成具体的行动计划。

- **执行动作** —— 没有智能体系统时，LLM 只会生成文本。放进智能体系统里，LLM 才能真正*执行*步骤——检索数据库、调用 API、发送消息。

- **可用的工具** —— 智能体能用哪些工具，取决于（1）它运行所处的环境，以及（2）开发者选择给了它什么。旅行智能体也许能查航班，但不能修改客户记录——完全取决于你接了什么进去。

- **记忆 + 知识** —— 智能体可以有短期记忆（当前这段对话）和长期记忆（客户数据库、过往交互）。旅行智能体可能会"记得"你偏好靠窗座位。

### AI 智能体的不同类型

智能体的构建方式各不相同。下面以旅行预订智能体为贯穿例子，梳理几种主要类型：

| **智能体类型** | **它做什么** | **旅行智能体示例** |
|---|---|---|
| **简单反射型智能体** | 按写死的规则行事——没有记忆，也不做规划。 | 看到一封投诉邮件 → 转给客服。仅此而已。 |
| **基于模型的反射型智能体** | 维护一个关于世界的内部模型，并随情况变化更新它。 | 跟踪历史机票价格，标记出突然变贵的航线。 |
| **目标驱动型智能体** | 心里有个目标，并一步步想办法达成。 | 从你当前所在地出发，把整趟行程（机票、租车、酒店）订好，把你送到目的地。 |
| **效用驱动型智能体** | 不满足于找到*一个*方案——通过权衡取舍找出*最优*的那个。 | 在成本与便利之间权衡，找出最符合你偏好的行程。 |
| **学习型智能体** | 从反馈中学习，随时间不断变好。 | 根据行程后的问卷结果调整今后的预订推荐。 |
| **分层式智能体** | 高层智能体把工作拆成子任务，分派给下层智能体。 | 一个"取消行程"请求被拆成：退机票、退酒店、退租车——各交给一个子智能体处理。 |
| **多智能体系统（MAS）** | 多个独立智能体协作（或竞争）。 | 协作式：分别由不同智能体负责酒店、航班和娱乐。竞争式：多个智能体竞相以最优价格把酒店房间卖出去。 |

## 何时使用 AI 智能体

*能*用 AI 智能体，不代表就*该*用。下面这些场景才是智能体真正发挥价值的地方：

![何时使用 AI 智能体？](../../../01-intro-to-ai-agents/images/when-to-use-ai-agents.png)

- **开放式问题** —— 当解决问题的步骤无法预先写死时。你需要 LLM 动态地找出路径。
- **多步骤流程** —— 需要跨多轮使用工具的任务，而不只是一次查询或一次生成。
- **随时间改进** —— 当你希望系统能根据用户反馈或环境信号变得更聪明时。

课程后面的 **构建可信赖的 AI 智能体** 一课，会更深入地讨论什么时候该用、什么时候*不*该用 AI 智能体。

## 智能体式方案基础

### 智能体开发

构建智能体的第一件事，是定义*它能做什么*——它的工具、动作和行为。

本课程用 LangChain 和 LangGraph、基于任意 OpenAI 兼容聊天模型来构建智能体。模型是可插拔的：只要改三个环境变量，同一份代码就能跑在 DeepSeek、OpenAI、MiniMax、本地 Ollama 服务或 vLLM 部署上。一个智能体由这几部分组成：

- 来自任意提供方的模型，只要它暴露支持工具调用的 OpenAI 兼容接口地址
- 来自你自己数据源的知识
- 工具：任何被暴露为工具的 Python 函数，或者一个 Model Context Protocol 服务器

### 智能体式模式

你通过提示词与 LLM 沟通。但用智能体时，你没法每条提示词都手工打磨——智能体需要跨很多步骤采取行动。这就轮到**智能体式模式**登场了。它们是一套可复用的策略，用更可扩展、更可靠的方式来给 LLM 写提示词并做编排。

本课程正是围绕这些最常见、最有用的智能体式模式来组织的。

### 智能体框架

智能体框架为开发者提供了现成的模板、工具和基础设施。它们让下面这些事更容易：

- 接好工具和各种能力
- 观察智能体正在做什么（出问题时便于调试）
- 让多个智能体协作

本课程聚焦 LangChain 1.x 和 LangGraph 1.x（https://docs.langchain.com/oss/python/langchain/overview），这是用于构建生产级智能体的开源框架。

## 作业：构建你自己的智能体

上面的 notebook 用四步构建了一个旅行助手：模型客户端、工具、智能体、流式回复。你的作业是在一个**不同的领域**里，按同样的四步构建一个属于你自己的智能体。可以参考这些方向：餐厅推荐、学习计划助手、电影挑选、礼物顾问、校园服务台。选一个你能用一句话说清楚的主题。

### 要求

1. **新建一个 notebook**，放在 `code_samples/` 目录下，命名为 `01-assignment-<你的主题>.ipynb`。开头使用与课程 notebook 相同的环境准备单元，从 `.env` 读取 `LLM_BASE_URL`、`LLM_API_KEY` 和 `LLM_MODEL`。绝不要把 API key 直接粘贴进 notebook。
2. **用 `@tool` 装饰器定义至少两个工具**。其中一个返回一个列表，类似 `get_destinations`；另一个必须接收至少一个参数并真正用到它，例如 `get_details(name: str)` 或 `search(keyword: str)`。两个工具都要有类型注解和一句话的 docstring，因为模型读的就是 docstring。数据可以直接写死在代码里。
3. **用 `create_agent` 创建智能体**。自己写一段系统提示词，说明智能体是谁、能帮什么忙，并要求它使用工具而不是凭空猜测。
4. **运行一次 `invoke` 调用**，并打印*完整*的消息历史，而不只是最终回复。遍历 `result["messages"]`，打印每条消息的类型和内容，让工具调用和工具结果都能看到。
5. **运行一次流式调用**，用 `astream(..., stream_mode="messages")` 问第二个问题，像课程 notebook 那样只打印来自模型节点的块。
6. **解释每一步**：在每个代码单元上方用一个简短的 markdown 单元、用你自己的话说明它在做什么。最后加一个三到五句话的 markdown 单元回答：模型什么时候调用了工具？什么时候没用工具就直接回答了？当你问到工具覆盖不到的内容时，发生了什么？

你的 notebook 必须能从上到下无错误地运行。用课程同样的方式检查它，在仓库根目录运行：

```bash
python scripts/validate_notebooks.py --path 01-intro-to-ai-agents/code_samples/01-assignment-<你的主题>.ipynb
```

### 提交前自查

- notebook 的代码里没有写死任何 API key、模型名或接口地址。
- 打印出的消息历史里至少能看到一次工具调用及其结果。
- 每个工具都有类型注解和 docstring；智能体的系统提示词里提到了这些工具。
- 流式回复是逐 token 打印出来的，而不是最后一次性输出一整块。
- 反思单元回答了全部三个问题。

### 进阶目标（可选）

- 让其中一个工具从文件或公开 API 读取数据，而不是用 Python 列表。
- 用第二次 `invoke` 调用问一个追问，观察智能体已经忘了第一个问题。第 02 课会教你用检查点器解决这个问题。
- 问智能体一个它的工具回答不了的问题，然后调整系统提示词，直到它老实承认不知道，而不是编造答案。
